# 新規参加者向けオンボーディングガイド

## 1. まず把握するべき全体像
このリポジトリは、**HTML/CSS/JavaScriptのみで動く静的Webアプリ**として、
「太陽光＋蓄電池の15年評価（利益・ROI・回収年数）を試算し、推奨案を表示する」ことを目的としています。サーバーサイド実装やビルド工程はありません。`README.md` も静的配信を前提とした起動方法になっています。

- エントリポイントは `index.html`。
- ロジックの中心は `app.js`。
- 見た目は `styles.css`。
- 設定値・候補値は `data/*.json`。

## 2. ディレクトリ構成（実務でよく触る場所）

- `index.html`
  - 入力フォーム、結果表示、工務店向け設定モーダルのDOMを定義。
- `app.js`
  - 料金換算、日次エネルギーフロー、15年便益、価格推定、候補探索、推奨案抽出、UI描画、設定保存（localStorage）までを一括で担当。
- `styles.css`
  - 画面レイアウト、カード、ボタン、モーダル等のスタイル。
- `data/feed_in_tariffs.json`
  - 年次売電単価のテーブル。
- `data/battery_sizes.json`
  - 探索対象の蓄電池容量。
- `data/panels.json` / `data/batteries.json`
  - 現状ロジックでは主計算に直接使わず、将来の製品選定拡張向けデータとして置かれている。
- `solar-selector-mvp/`
  - ルート配下と類似ファイルを持つ別ディレクトリ。運用中の起点をチームで明示しておかないと混乱しやすいので注意。

## 3. 重要ロジック（読み始める順番）

1. **デフォルト設定と保存まわり**
   - `DEFAULTS` に工務店向けの前提値（利益率、固定費、夜間比率、探索範囲など）がまとまっている。
   - `getSettings` / `saveSettings` / `isUnlocked` で localStorage 永続化。

2. **データロード**
   - `loadData()` が `feed_in_tariffs.json` と `battery_sizes.json` を読み込み。
   - fetch失敗時はデフォルト値にフォールバック。

3. **試算ロジック**
   - `billToUsageKwhMonth`: 電気代→月間使用量(kWh)へ変換。
   - `dailyFlows`: PV発電→昼消費→充電→夜消費→売電 の単純モデル。
   - `estimate15yEconomics`: 評価期間分の便益（自家消費＋売電）を積算。
   - `estimateCustomerPrice`: PV/蓄電池容量から概算価格レンジを算出。
   - `evaluateCombo`: 便益と価格から純利益、ROI、回収年数を算出。

4. **探索・推奨表示**
   - PVを刻み幅で走査し、蓄電池容量候補と組み合わせて評価。
   - 表示設定に応じて「PVのみ」「蓄電池あり」「全体最短回収」「工務店作成」などをカード表示。

## 4. 新規参加者が最初に知るべき重要事項

- **ローカルサーバー必須**
  - JSONをfetchするため、`file://` 直開きでは動かない。
- **localStorage依存**
  - 工務店設定・ロック状態はブラウザに保存される。検証時はストレージ初期化の影響を意識する。
- **簡易モデルであること**
  - 影・方位・季節変動・劣化・契約詳細などは非考慮。営業用の概算補助という位置づけ。
- **探索粒度に伴う計算コスト**
  - 既定でPVが0.01刻みなので、範囲を広げると評価件数が増える。
- **ルートと `solar-selector-mvp/` の二重管理リスク**
  - どちらを正として更新するかを決めておかないと差分が乖離しやすい。

## 5. 次に学習すべきテーマ（優先順）

1. **UIイベント→計算→描画の呼び出し経路を追う**
   - 「診断する」クリック時の処理から、結果カード描画までをトレースする。
2. **計算前提のドメイン妥当性を確認する**
   - 固定費、夜間比率、発電量、売電単価セグメントが実運用に合っているかを関係者レビュー。
3. **データモデルの拡張方針を固める**
   - `panels.json` / `batteries.json` を実際の候補最適化に組み込むか、現状維持かを決定。
4. **テスト戦略を整備する**
   - 現状は手動確認中心。純関数（料金換算、日次フロー、回収年数）を切り出してユニットテスト可能にすると保守しやすい。
5. **重複ディレクトリの整理**
   - ルート版と `solar-selector-mvp/` のどちらを本番系とするかを明文化し、不要側をアーカイブして誤更新を防ぐ。

## 6. 開発の進め方（最短ルート）

1. `python -m http.server 8000` などで起動。
2. `index.html` + `app.js` をセットで読み、入力→結果表示までの流れを理解。
3. `data/feed_in_tariffs.json` と `data/battery_sizes.json` を編集して挙動変化を確認。
4. 変更時は以下観点で手動確認：
   - 入力未指定時のデフォルト適用
   - 予算制約あり/なし
   - 蓄電池ON/OFF
   - 評価期間変更
   - 工務店設定ロック/解除

この順で把握すると、実務上の改修ポイント（ロジック変更・表示変更・初期値調整）に短時間で入れます。
